# Quest 2 stereo and performance follow-up

Date: 2026-09-29. Scope: the published Babylon streamed SOG walking prototype and a localhost candidate on the same USB-connected Quest 2. The local candidate has no commit SHA; this repository still has no HEAD commit.

## Findings

1. **Right-eye sort starvation.** Babylon 9.28 keeps a sorted splat index buffer per camera but posts one sort job at a time. In the published build, the left eye repeatedly submitted a new sort before the right eye received its first buffer. A Quest Browser trace recorded 493 left-eye requests and 7 right-eye requests in the latest 500 jobs, with the right eye's first request about 2.5 seconds after the sampled left-eye request. The published build could eventually show both eyes when stationary, so the black-eye report is consistent with startup or continued motion rather than a permanently missing XR viewport.
2. **GPU load.** The published build used a 2880×1584 stereo XR layer (roughly 1440×1584 per eye), about 269,000 rendered splats, and no fixed foveation. The XR callback median was about 95 ms in a stationary ADB-driven run; `ovrgpuprofiler -r` showed about 88% GPU utilization and 96% shader busy. Changing only the live XR layer's fixed foveation from 0 to 1 reduced the median to about 73 ms. This supported a GPU rendering bottleneck. The source SOG's coarsest LOD has 196,908 splats, so a lower budget cannot help without changing the asset or renderer.
3. **XR detail collapsed to the base layer.** The 200,000-splat XR cap produced exactly 199,792 sorted splats on the Quest. Its 1440×792 stereo layer is roughly 720×792 per eye, a 75% pixel reduction from the original layer. The cap is effectively the coarse base layer plus environment, leaving no material budget for finer streamed levels. A CDP trace showed additional chunks fetched during the initial desktop phase, then active ranges shrank when XR began. The user's observation that detail does not appear to stream in VR is consistent with this trace.
4. **A one-eye blank frame on LOD count changes is reproduced.** Claude traced Babylon 9.28's worker result handler: when the selected splat count changes, it binds a new zero-filled index array to every camera's separate GPU buffer, then fills and uploads only the camera whose sort completed. In a real WebGL2 split-view reproduction with 4,000 splats and two cameras, each of six count changes produced one near-empty right-eye frame (1,737 lit pixels versus 160,000 normally); both eyes recovered after the right-eye sort. The same code path is used by the Quest, but the actual Quest event has not yet been time-correlated with a count change.
5. **Compositor-wide flicker remains unresolved.** The owner reports separate eye flicker during navigation and whole-headset flicker when the scene is in the background. The buffer defect explains a scene-eye blank frame but cannot by itself explain a system-wide flash. No Quest trace yet distinguishes frame stalls, visibility transitions, or a compositor problem. The 200,000-splat draft must not be promoted on the strength of the earlier stationary stereo screenshot.

## Candidate and checks

- `prepareStereoSplatSort` gives Babylon's sorter both rig cameras before the per-eye render pass, then restores `scene.activeCameras`. This uses the library's existing priority for eyes with no completed sort. The first localhost candidate recorded 25 left and 27 right sorts, with the right eye scheduled within about 0.4 seconds; its XR callback median remained about 100 ms at the published render settings.
- The second localhost candidate sets the XR splat budget to 200,000, requests a 0.5 framebuffer scale with no XR layer antialiasing, and sets fixed foveation to 1. The Quest reported a 1440×792 stereo layer, fixed foveation 1, and about 199,792 rendered splats. A stationary stereo screenshot showed the scene in both eyes. The latest warmed 500-frame sample lasted 6.35 seconds: callback interval p10 11.29 ms, median 12.34 ms, p90 14.97 ms, p99 18.31 ms. The last 500 sort requests split 251 left / 249 right. This is a frame callback sample, not a compositor FPS or comfort measurement. The 90 Hz / 11.1 ms measurement target was not met consistently.
- The stereo regression test was strengthened after Claude's independent review to exercise Babylon's actual 9.28.0 sort method with two moving cameras and a stub worker. Disabling the preparation made the test fail with six left-eye jobs; restoring it made the first six jobs alternate left/right. The candidate archive SHA-256 was `bfc9b852afe906e1605b2c692e58543231391fef408daac63abf5ef79fa57f6f` on both cloud and Mac.
- A third local build raises the XR cap to 300,000. Its archive SHA-256 is `ef494cd6513a2fec62d6a11c5e90ca6d13719a4fd2ee07be1e218b04536aabda` on both cloud and Mac. It is served at Quest localhost port 55003, but has not entered immersive VR: Quest Browser reports another active immersive session. In a separate Mac Chrome session at a 1440×705 canvas, changing the live stream budget from 200,000 to 300,000 changed the selected count from 199,885 (210 nodes at level 4) to 258,908 (144 nodes at level 4 and 73 finer nodes). Moving that test camera to an unvisited region fetched seven WebP textures each for files `2_0`, `1_0`, `0_0`, and `1_1`. This verifies budget-driven refinement and on-demand network streaming for that desktop camera, not XR frame rate or visual comfort.
- A fourth local source candidate adds `syncStereoSplatIndexBuffers`. When Babylon's shared index array identity changes, it uploads the filled indices to both eye meshes before the eye pass. Claude ran the actual helper in a WebGL2 reproduction: nine LOD count changes over 260 frames produced zero blank-eye frames with the helper versus 16 without; a parent-camera-sort variant produced zero versus 28. The first test only counted upload calls, so it was replaced with a stronger regression that invokes Babylon's real worker reply on `NullEngine`, spies on dynamic vertex-buffer data, observes `[0, 0]` in the other eye after resize, and fails without the helper. `npm run check` passes 19 tests and `npm run build` succeeds. The exact current build archive SHA-256 `1425f2e48cf514a36349a21f917e1fae79ce12702e5be24f030872205ddf2874` matches on cloud and Mac, is served on Mac localhost port 55005, and reached “Scene ready” in isolated desktop Chrome without uncaught errors. The code moves synchronization to `onBeforeCameraRenderObservable` and guards disposed streams. Quest USB disconnected while preparing the reverse port, so immersive verification remains pending. Claude's follow-up found no blocking code issue; it did not verify WebXR on the headset.
- The **second, 200,000-splat build** was uploaded through the Mac CLI as isolated Netlify draft `6abc2235f9209b0b37d7e9d5` at `https://6abc2235f9209b0b37d7e9d5--ronda-lobato-babylon-sog-walk.netlify.app/`. Unauthenticated GET returned HTTP 200; downloaded HTML and main JS SHA-256 hashes exactly matched that build's `dist`. The hosted browser smoke test reached “Scene ready,” fetched the SOG manifest and WebP chunks, exercised pointer lock and Escape, and reported no page errors.
- The **fourth, 300,000-splat build** was uploaded as draft `6abc33c30e0da3b92620c5be`. Its HTML and main JavaScript SHA-256 hashes matched the freshly checked `dist`; the draft browser smoke test reached “Scene ready,” fetched the manifest and chunks, exercised pointer lock and Escape, and reported no page errors. After exact-action owner approval, that draft was published to production on 2026-09-29. Netlify reports it as the published deploy; the live files match the same hashes and the live browser smoke test passed. Previous production deploy `6abbe613c767a317895b5f12` is retained for rollback.

## Limits and release state

The desktop browser cannot establish Quest visual quality or comfort. The owner initially confirmed that both eyes show the scene and walking feels usable in the 200,000-splat localhost candidate, then reported the remaining black flicker and missing XR detail. The performance settings trade resolution and antialiasing for speed, and the GPU still reports roughly 88% utilization during the warmed 200,000-splat candidate sample. The 300,000-splat source was verified on desktop and published at the owner's request with the headset result explicitly unverified. Its Quest flicker and performance still need a headset retest.

Claude independently reviewed the current uncommitted stereo and index-buffer code, ran `npm run check` and `npm run build`, and found no blocking code issue. Its real WebGL2 test exercised the exact helper but used split desktop viewports and synthetic splats. Remaining lower-severity limits: temporary `scene.activeCameras` assignment allocates wrappers each frame; same-padded-count range changes can briefly leave old indices in the other eye; and a forced sort during chunk loading may target the parent XR camera. The Quest-only compositor and performance questions remain open.
